## Objectif

L'OVHcloud Load Balancer agit comme un proxy entre vos clients et vos serveurs backend. De ce fait, vos serveurs backend voient l'adresse IP de sortie du Load Balancer comme source de chaque connexion, et non l'adresse réelle du client. Le ProxyProtocol rétablit cette information en ajoutant un petit en-tête au début de chaque connexion TCP, ce qui permet au backend de récupérer l'adresse IP, le port et le protocole d'origine du client.

**Ce guide explique comment activer le ProxyProtocol sur un serveur backend de votre OVHcloud Load Balancer et comment configurer le serveur pour qu'il accepte et analyse l'en-tête ProxyProtocol.**

> [!TIP]
> Si votre frontend utilise le protocole HTTP, utilisez des en-têtes HTTP (tels que `X-Forwarded-For`) plutôt que le ProxyProtocol. Reportez-vous au guide [Configurer les en-têtes HTTP](/guides/network/load-balancer-revamp/configure-http-headers). Le ProxyProtocol est destiné aux frontends TCP, pour lesquels les en-têtes HTTP ne sont pas disponibles.

## Prérequis

- Un [compte OVHcloud](/links/manager) actif
- Un accès à l'[espace client OVHcloud](/links/manager)
- Un OVHcloud Load Balancer disposant d'un frontend TCP fonctionnel et d'une ferme de serveurs — consultez le guide [Configurer les fermes de serveurs](/guides/network/load-balancer-revamp/configure-server-farms)
- Un serveur backend exécutant un logiciel qui prend en charge le ProxyProtocol (par exemple Nginx, Apache ou HAProxy)
- Être familiarisé avec les frontends et les fermes de serveurs — consultez le guide [Quickstart : TCP](/guides/network/load-balancer-revamp/quickstart-tcp)

> [!warning]
> Les champs du ProxyProtocol peuvent être falsifiés par un client malveillant : ne leur faites donc confiance que lorsqu'ils proviennent d'une source de confiance. Restreignez l'analyse du ProxyProtocol sur vos serveurs backend aux adresses IP de sortie de votre OVHcloud Load Balancer, comme décrit dans la section [Configurer votre serveur backend pour qu'il accepte le ProxyProtocol](#trust-proxyprotocol) ci-dessous.

## Introduction

Le ProxyProtocol a été développé par l'équipe [HAProxy](https://www.haproxy.org/) comme l'équivalent TCP des en-têtes HTTP tels que `X-Forwarded-For`. Lorsqu'il est activé pour un serveur backend, le Load Balancer ajoute un en-tête qui contient au minimum :

- Le protocole de couche 4 utilisé (`TCP4` pour l'IPv4 ou `TCP6` pour l'IPv6).
- L'adresse source IPv4 ou IPv6.
- Le port source.

Étant donné que l'en-tête modifie le début du flux TCP, le serveur backend doit être configuré pour s'y attendre et l'analyser. Le protocole existe en deux versions :

| Version | Format | Remarques |
|---|---|---|
| Version 1 | Texte | La plus largement prise en charge. Suffisante pour la plupart des cas d'usage. |
| Version 2 | Binaire | Plus rapide à analyser. Peut également transporter des informations SSL/TLS ainsi que le Common Name du certificat. |

Votre OVHcloud Load Balancer prend en charge quatre modes de ProxyProtocol :

| Mode | Description |
|---|---|
| `v1` | Version 1 au format texte. Le mode le plus largement pris en charge. |
| `v2` | Version 2 au format binaire, sans options. |
| `v2-ssl` | Version 2 avec un champ décrivant la connexion SSL, le cas échéant. |
| `v2-ssl-cn` | Version 2 avec le champ SSL et le `Common Name` du certificat, le cas échéant. |

Le ProxyProtocol s'active par serveur, et non par ferme. Cela vous permet de le tester sur un seul backend avant de l'appliquer à l'ensemble d'une ferme active. Lorsque le ProxyProtocol est activé pour un serveur, les sondes insèrent également l'en-tête, sauf si un port de sonde dédié est configuré — dans ce cas, la sonde se connecte sans l'en-tête.

Pour la spécification complète, reportez-vous à la [spécification du ProxyProtocol](https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt).

## En pratique

L'activation du ProxyProtocol comporte deux parties. Tout d'abord, activez le mode ProxyProtocol sur le serveur backend dans votre OVHcloud Load Balancer. Ensuite, configurez ce serveur backend pour qu'il accepte et analyse l'en-tête.

### Trouver les adresses IP de sortie de votre Load Balancer

Pour configurer la confiance sur vos serveurs backend, vous avez besoin de la liste des adresses IP de sortie de votre OVHcloud Load Balancer. Récupérez-les avant de commencer.

3. Notez les adresses IPv4 de sortie affichées sur le tableau de bord du service.

### Activer le ProxyProtocol sur un serveur backend

Activez un mode ProxyProtocol sur le serveur cible. La propriété de serveur correspondante dans l'API est `proxyProtocolVersion`.

<Tabs>
<Tab label="Espace client">

1. Connectez-vous à l'<ManagerLink to="/">espace client OVHcloud</ManagerLink> et ouvrez votre service Load Balancer.
2. Sélectionnez l'onglet `Fermes de serveurs`.
3. Ouvrez la ferme qui contient le serveur cible, puis modifiez ce serveur.
4. Définissez le mode ProxyProtocol sur `v1`, `v2`, `v2-ssl` ou `v2-ssl-cn`.
5. Enregistrez le serveur, puis appliquez la configuration à la zone concernée.

### Configurer votre serveur backend pour qu'il accepte le ProxyProtocol

Une fois le ProxyProtocol activé du côté du Load Balancer, configurez le serveur backend pour qu'il s'attende à l'en-tête, l'analyse et lui fasse confiance. Restreignez toujours la confiance aux adresses IP de sortie récupérées précédemment. Les exemples ci-dessous utilisent la plage fictive `10.108.0.0/14` — remplacez-la par vos propres adresses de sortie.

#### Nginx

Nginx prend en charge la version 1 du ProxyProtocol et expose l'adresse du client via la variable `proxy_protocol_addr`. Avec le module `ngx_http_realip`, Nginx utilise cette variable comme adresse source réelle dans les journaux.

```nginx
server {
    # Enable ProxyProtocol on port 80
    listen 80 proxy_protocol;

    # Trust ProxyProtocol only from your Load Balancer outbound addresses
    set_real_ip_from 10.108.0.0/14;
    real_ip_header proxy_protocol;

    # (optional) Forward the real client IP in headers
    proxy_set_header X-Real-IP        $proxy_protocol_addr;
    proxy_set_header X-Forwarded-For  $proxy_protocol_addr;

    # Your regular configuration here
    # ...
}
```

Rechargez la configuration :

```bash
service nginx reload
```

Pour plus d'informations, reportez-vous à la [documentation Nginx sur le ProxyProtocol](https://docs.nginx.com/nginx/admin-guide/load-balancer/using-proxy-protocol/).

#### Apache

Apache prend en charge le ProxyProtocol via le module `mod_remoteip`, qui gère également les en-têtes `X-Forwarded-For` et vous permet de contrôler les adresses auxquelles le ProxyProtocol s'applique.

Avant d'activer le ProxyProtocol, restreignez les connexions aux adresses de sortie de votre OVHcloud Load Balancer avec `iptables` :

```bash
# Trust connections from your Load Balancer outbound addresses only
iptables -A INPUT -s 10.108.0.0/14 -p tcp --dport 80 -j ACCEPT
iptables -A INPUT                  -p tcp --dport 80 -j DROP
```

Configurez l'hôte virtuel pour activer le ProxyProtocol :

```apache
<VirtualHost *:80>
    RemoteIPProxyProtocol On
    # ...
</VirtualHost>
```

Remplacez `%h` par `%a` dans les directives `LogFormat` afin que les journaux enregistrent l'adresse réelle du client. Activez ensuite le module et redémarrez Apache :

```bash
# Enable the remoteip module
a2enmod remoteip

# Restart Apache to load the module
service apache2 restart
```

Pour plus d'informations, reportez-vous à la [documentation de mod_remoteip](https://httpd.apache.org/docs/trunk/mod/mod_remoteip.html#remoteipproxyprotocol).

#### HAProxy

Le ProxyProtocol a été conçu par l'équipe HAProxy, qui le gère donc parfaitement. Un modèle courant consiste à placer une instance HAProxy locale devant un logiciel qui ne prend pas en charge le ProxyProtocol (comme MySQL ou PostgreSQL) afin de récupérer et de journaliser l'adresse IP du client.

L'exemple suivant écoute sur le port TCP 3306 pour MySQL. Il s'agit d'un point de départ, et non d'une configuration complète.

Installez HAProxy :

```bash
sudo apt install haproxy
```

Configurez le proxy local :

```text
listen mysql
    # Listen on all interfaces, port 3306, TCP mode
    mode tcp
    option tcplog
    bind *:3306

    # Expect the ProxyProtocol header only from a trusted network
    tcp-request connection expect-proxy layer4 if { src 10.108.0.0/14 }

    # Forward to the local MySQL server on a non-standard port
    server mysql 127.0.0.1:3316 check
```

Rechargez la configuration :

```bash
service haproxy reload
```

### Obligations légales

Les lois et réglementations applicables peuvent vous imposer de conserver des journaux et certaines données de trafic. La conservation de l'adresse IP réelle du client grâce au ProxyProtocol peut faire partie des moyens de respecter ces obligations. Il vous incombe de vous conformer aux lois qui vous sont applicables. Par exemple, l'[Investigatory Powers Act 2016 (Section 87)](https://www.legislation.gov.uk/ukpga/2016/25/section/87) peut imposer aux opérateurs de télécommunications de conserver certaines données de communication, y compris les données identifiant la source et la destination d'une communication.

OVHcloud met à votre disposition des services dont vous êtes responsable de la configuration et de la gestion.
