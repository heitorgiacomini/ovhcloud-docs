## Objectif

Ce guide explique comment activer le transfert des logs depuis votre OVHcloud Load Balancer vers Logs Data Platform (LDP). Une fois le transfert activé, les logs d'accès générés par vos listeners TCP, HTTP et HTTPS sont ingérés dans un flux de données Logs Data Platform, où vous pouvez les stocker, les interroger et les visualiser.

**Dans ce guide, vous apprendrez à :**

- Préparer votre Load Balancer en rafraîchissant sa configuration afin que le format de logging soit à jour.
- Récupérer le flux de données cible de votre compte Logs Data Platform.
- Créer un abonnement aux logs pour démarrer leur transfert.
- Vérifier l'abonnement et consulter les logs transférés.
- Gérer et résilier un abonnement existant.

:::warning
Les logs des listeners **UDP** ne sont pas transférés. Seuls les logs des listeners TCP, HTTP et HTTPS sont pris en charge.
:::

## Prérequis

- Un [OVHcloud Load Balancer](/guides/network/load-balancer-revamp/what-is-load-balancer) opérationnel.
- Un [compte Logs Data Platform](/guides/manage-and-operate/observability/logs-data-platform/getting-started-quick-start) avec au moins un flux de données actif configuré.
- Le compte Logs Data Platform et l'OVHcloud Load Balancer doivent appartenir au même compte OVHcloud.
- Des identifiants d'API OVHcloud (application key, application secret, consumer key). Consultez le guide [Premiers pas avec l'API OVHcloud](/guides/manage-and-operate/api/first-steps).
- Un accès à l'<ManagerLink to="/">espace client OVHcloud</ManagerLink>.

:::tip
Si vous ne connaissez pas bien la configuration d'un flux de données Logs Data Platform, créez un nouveau flux avec les options par défaut (indexation et websocket activés, stockage à long terme désactivé) pour ce guide.
:::

## Introduction

L'OVHcloud Load Balancer repose sur [HAProxy](https://en.wikipedia.org/wiki/HAProxy), le composant open source utilisé pour la répartition de charge. Les logs d'accès transférés vers Logs Data Platform sont produits par HAProxy. Logs Data Platform (LDP) est une plateforme de gestion de logs entièrement managée et exploitée par OVHcloud, qui vous permet d'ingérer, de stocker, d'archiver, d'interroger et de visualiser des logs à travers un flux de données.

Le transfert des logs ingère les logs d'un service OVHcloud dans un flux de données LDP au sein du même compte OVHcloud. Il s'active service par service. Lorsque vous activez le transfert d'un Load Balancer vers un flux de données, un *abonnement* est créé et rattaché à ce flux pour sa gestion ultérieure.

L'activation du transfert est gratuite. Vous êtes facturé pour votre utilisation de Logs Data Platform selon la grille tarifaire standard. Pour en savoir plus, consultez la [tarification de Logs Data Platform](/guides/manage-and-operate/observability/logs-data-platform/getting-started-quick-start) et la [page du service LDP](/links/manage-operate/ldp).

### Fonctionnement du transfert <a name="how-it-works"></a>

Le transfert est activé par Load Balancer et par type de log (`tcp` ou `http`). Chaque activation crée un abonnement qui relie votre Load Balancer à un unique flux de données Logs Data Platform. Le schéma suivant illustre le flux de bout en bout.

<img className="thumbnail" alt="Fonctionnement du transfert — schéma" src="/images/network/load-balancer-revamp/configure-logs-forwarding/fig-1.fr.svg" loading="lazy" />

| Terme | Signification |
|---|---|
| Flux de données | Une partition logique des logs dans un compte LDP. Il s'agit de l'unité utilisée pour définir la rétention, l'archivage, le streaming en direct, les droits d'accès et les politiques d'alerte. |
| Transfert des logs | La fonctionnalité qui ingère les logs du Load Balancer dans un flux de données LDP. Activée service par service. |
| Abonnement | L'objet créé lorsque le transfert est activé. Il rattache les logs du Load Balancer à un flux de données donné et sert à sa gestion ultérieure. |
| Type de log | La catégorie de logs à transférer : `tcp` ou `http`. Récupérée via l'endpoint d'API dédié au type de log. |

### Référence du contenu des logs <a name="log-content"></a>

Les champs décrits ci-dessous sont présents dans les logs transférés. Le premier tableau s'applique à tous les listeners basés sur TCP (types `tcp` et `http`). Le second tableau liste les champs supplémentaires présents pour les listeners `http`.

#### Champs pour les listeners basés sur TCP (`tcp`, `http`)

| Nom du champ | Description | Type |
|---|---|---|
| `service_name` | Le nom du Load Balancer qui a reçu la requête ou la connexion. | Chaîne de caractères |
| `date_time` | L'horodatage auquel la requête ou la connexion a été effectuée. | Date/heure, résolution à la milliseconde (par exemple `25/Mar/2024:14:07:19.536`) |
| `zone` | La région OVHcloud à laquelle appartient le Load Balancer. | Chaîne de caractères |
| `client_ip` | L'adresse IP du client qui a initié la connexion TCP. | IP |
| `client_port_int` | Le port TCP du client qui a initié la connexion TCP. | Entier |
| `frontend_name` | Le nom du frontend de votre Load Balancer. | Chaîne de caractères |
| `frontend_ip` | L'adresse IP du frontend de votre Load Balancer. | IP |
| `frontend_port_int` | Le port TCP du frontend de votre Load Balancer. | Entier |
| `backend_name` | Le nom de la source NAT utilisée par le Load Balancer pour se connecter à vos serveurs backend. | Chaîne de caractères |
| `backend_source_ip` | L'adresse IP source utilisée par le Load Balancer pour se connecter à vos serveurs backend. | IP |
| `backend_source_port_int` | Le port source utilisé par le Load Balancer pour se connecter à vos serveurs backend. | Entier |
| `server_ip` | L'adresse IP du serveur backend connecté à votre Load Balancer. | IP |
| `server_port_int` | Le port TCP du serveur backend connecté à votre Load Balancer. | Entier |
| `termination_state` | L'indicateur de fin de session : 2 lettres pour TCP, 4 lettres pour HTTP. Consultez la [documentation HAProxy](https://docs.haproxy.org/2.6/configuration.html#8.5). | Chaîne de caractères (par exemple `----`) |
| `bytes_read_int` | La taille, en octets, de la réponse envoyée par le Load Balancer au client. | Entier |
| `bytes_uploaded_int` | La taille, en octets, de la requête envoyée par le client au Load Balancer. | Entier |
| `time_duration_int` | La durée, en millisecondes, de la session TCP au moment où la requête a été effectuée. | Entier |

#### Champs supplémentaires pour les listeners `http`

| Nom du champ | Description | Type |
|---|---|---|
| `captured_request_headers` | Les en-têtes de la requête HTTP (par exemple `User-Agent`). | Chaîne de caractères |
| `http_request` | La ressource de la requête HTTP (par exemple `/index.html`). | Chaîne de caractères |
| `http_status_code_int` | Le statut HTTP retourné (par exemple `200`). | Entier |

### Étape 1 — Rafraîchir la configuration du Load Balancer <a name="step-1"></a>

Avant de transférer le moindre log, rafraîchissez le Load Balancer dont vous souhaitez collecter les logs. Cette opération applique la configuration actuelle et garantit que le format de logging est à jour.

Vous avez besoin du `serviceName`, qui est le nom interne de votre Load Balancer. Vous pouvez le trouver sur la page de gestion du Load Balancer dans l'<ManagerLink to="/">espace client OVHcloud</ManagerLink> (<code className="action">Network</code> > <code className="action">Load Balancer</code>), ou en listant vos services via l'API.

<Api version="v1" section="/ipLoadbalancing" method="GET" route="/ipLoadbalancing" />

Appliquez ensuite la configuration :

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/refresh"} />

| Paramètre | Requis | Description | Exemple |
|---|---|---|---|
| `serviceName` | Oui | Le nom interne de votre Load Balancer. | `loadbalancer-xxxxxxxxxxxxxxxxxxxx` |

### Étape 2 — Récupérer votre flux de données cible <a name="step-2"></a>

Identifiez le flux de données Logs Data Platform qui recevra vos logs. Vous avez besoin de son `streamId` pour créer l'abonnement à l'étape suivante.

Récupérez la liste des flux et les détails d'un flux spécifique depuis votre compte Logs Data Platform. Ces appels utilisent la section d'API `/dbaas/logs`. Indiquez le nom de votre service LDP sous la forme `ldp-xx-xxxx` comme `serviceName`.

| Action | Endpoint | Méthode |
|---|---|---|
| Lister les flux de données | `/dbaas/logs/{serviceName}/output/graylog/stream` | GET |
| Obtenir les détails d'un flux de données | `/dbaas/logs/{serviceName}/output/graylog/stream/{streamId}` | GET |

Vous pouvez également récupérer le `streamId` depuis l'interface de Logs Data Platform. Pour en savoir plus, consultez le guide [Démarrage rapide de Logs Data Platform](/guides/manage-and-operate/observability/logs-data-platform/getting-started-quick-start).

:::info
Notez la valeur du `streamId` (par exemple `18d602ec-af40-4000-8e59-41ecc8c23f80`). Vous la transmettez à l'appel d'abonnement à l'étape 3.
:::

### Étape 3 — Créer l'abonnement aux logs <a name="step-3"></a>

Créez un abonnement qui relie les logs de votre Load Balancer au flux de données cible. C'est cet appel qui active le transfert.

Tout d'abord, listez les types de logs disponibles pour votre Load Balancer afin de choisir la bonne valeur de `kind` :

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/log/kind"} />

Créez ensuite l'abonnement :

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/log/subscription"} />

| Paramètre | Requis | Description | Exemple |
|---|---|---|---|
| `serviceName` | Oui | Le nom interne de votre Load Balancer. | `loadbalancer-xxxxxxxxxxxxxxxxxxxx` |
| `kind` (corps) | Oui | Le type de log à transférer : `http` ou `tcp`. | `http` |
| `streamId` (corps) | Oui | Le flux de données LDP cible qui recevra les logs. | `18d602ec-af40-4000-8e59-41ecc8c23f80` |

**Exemple de corps de requête :**

```json
{
  "kind": "http",
  "streamId": "18d602ec-af40-4000-8e59-41ecc8c23f80"
}
```

**Exemple de réponse :**

```json
{
  "operationId": "f550aa1c-89ab-4b1a-81ae-4fba4959966f",
  "serviceName": "ldp-xxxxx"
}
```

La réponse renvoie un `operationId`. Vous l'utilisez à l'étape suivante pour récupérer le `subscriptionId` résultant.

### Étape 4 — Vérifier l'abonnement <a name="step-4"></a>

Confirmez que l'abonnement a bien été créé et que le transfert est actif.

Une fois l'opération terminée, listez les abonnements de votre Load Balancer pour récupérer le `subscriptionId` :

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/log/subscription"} />

Obtenez ensuite les détails d'un abonnement spécifique :

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/log/subscription/\{subscriptionId\}"} />

**Exemple de réponse :**

```json
{
  "createdAt": "2026-06-05T13:41:19.713Z",
  "kind": "http",
  "resource": {
    "name": "string",
    "type": "string"
  },
  "serviceName": "loadbalancer-xxxxxxxxxxxxxxxxxxxx",
  "streamId": "18d602ec-af40-4000-8e59-41ecc8c23f80",
  "subscriptionId": "19717204-2e10-4000-8c42-d7b11c9ce680",
  "updatedAt": "2026-06-05T13:41:19.713Z"
}
```

Pour récupérer le `subscriptionId` directement depuis l'opération, vous pouvez également interroger les détails de l'opération avec la section `/dbaas/logs` :

| Action | Endpoint | Méthode |
|---|---|---|
| Obtenir les détails de l'opération | `/dbaas/logs/{serviceName}/operation/{operationId}` | GET |

| Vérification | Comment | Résultat attendu |
|---|---|---|
| L'abonnement existe | Listez les abonnements aux logs. | Le `subscriptionId` apparaît dans la réponse. |
| L'abonnement cible le bon flux | Obtenez les détails de l'abonnement. | Le `streamId` correspond à votre flux de données cible. |
| Les logs arrivent | Ouvrez l'interface web Graylog de votre compte LDP. | De nouvelles entrées du Load Balancer apparaissent dans le flux de données. |

### Consulter les logs transférés <a name="view-logs"></a>

Une fois les logs ingérés dans votre flux de données Logs Data Platform, vous pouvez les interroger et créer des tableaux de bord via l'interface web Graylog.

1. Dans l'<ManagerLink to="/">espace client OVHcloud</ManagerLink>, récupérez le nom d'utilisateur LDP (par exemple `logs-xxxx`) et son mot de passe depuis la page d'accueil de votre compte Logs Data Platform. Consultez le guide [Démarrage rapide de Logs Data Platform](/guides/manage-and-operate/observability/logs-data-platform/getting-started-quick-start).
2. Ouvrez l'interface web Graylog. Le lien est disponible sur la page d'accueil de votre compte ou via votre point d'accès, selon la région de votre compte (par exemple, pour la région de Gravelines, il s'agit de `https://gra1.logs.ovh.com/`).
3. Connectez-vous à Graylog avec votre nom d'utilisateur et votre mot de passe Logs Data Platform.
4. Effectuez des recherches dans vos logs à travers le flux de données. Pour la syntaxe de recherche, consultez la documentation [Graylog writing search queries](https://go2docs.graylog.org/current/making_sense_of_your_log_data/writing_search_queries.html).

:::tip
L'onglet `Logs` sur la page du Load Balancer dans l'espace client vous permet de visualiser l'activité récente de votre service. Pour le stockage à long terme, les alertes, le streaming WebSocket en temps réel, OpenSearch Dashboards et l'intégration Grafana, utilisez Logs Data Platform.
:::

### Gérer et résilier un abonnement <a name="manage"></a>

Vous pouvez résilier le transfert à tout moment en supprimant l'abonnement. Après suppression, le flux de données ne reçoit plus de nouveaux logs du Load Balancer.

:::warning
La suppression d'un abonnement arrête le transfert des nouveaux logs. Elle ne supprime pas les logs déjà stockés avant la résiliation. Les données stockées dans un flux de logs sont immuables, à moins que vous ne supprimiez l'intégralité du flux.
:::

Supprimez l'abonnement avec l'appel suivant :

<Api version="v1" section="/ipLoadbalancing" method="DELETE" route={"/ipLoadbalancing/\{serviceName\}/log/subscription/\{subscriptionId\}"} />

| Paramètre | Requis | Description | Exemple |
|---|---|---|---|
| `serviceName` | Oui | Le nom interne de votre Load Balancer. | `loadbalancer-xxxxxxxxxxxxxxxxxxxx` |
| `subscriptionId` | Oui | L'identifiant de l'abonnement à supprimer. | `19717204-2e10-4000-8c42-d7b11c9ce680` |

Les abonnements de transfert des logs se gèrent uniquement via l'API OVHcloud. Le provider Terraform OVHcloud permet de gérer les fermes, les serveurs et les routes du Load Balancer (par exemple `ovh_iploadbalancing_http_farm`, `ovh_iploadbalancing_tcp_farm`), mais il ne propose pas de ressource pour les abonnements aux logs : utilisez donc les appels d'API ci-dessus pour les créer et les supprimer.

### Limites <a name="limitations"></a>

Cette section liste les contraintes connues du transfert des logs du Load Balancer.

| Limite | Détails |
|---|---|
| Listeners UDP | Les logs des listeners UDP ne sont pas transférés. Seuls les types `tcp` et `http` sont pris en charge. |
| Même compte | Le compte Logs Data Platform et le Load Balancer doivent appartenir au même compte OVHcloud. |
| Activation depuis l'espace client | L'activation du transfert (la création d'un abonnement) s'effectue via l'API OVHcloud. Cette fonctionnalité n'est pas encore disponible dans l'espace client. |
| Historique immuable | La résiliation d'un abonnement ne supprime pas les logs déjà stockés dans le flux de données. |

### Résolution des problèmes <a name="troubleshooting"></a>

Cette section couvre les problèmes les plus courants lors de la mise en place du transfert des logs.

| Problème | Cause possible | Solution |
|---|---|---|
| Aucun log n'apparaît dans le flux de données | La configuration du Load Balancer n'a pas été rafraîchie. | Exécutez l'appel de rafraîchissement de l'[Étape 1](#step-1) et attendez la fin de l'opération. |
| Aucun log n'apparaît dans le flux de données | L'abonnement cible le mauvais `streamId`. | Obtenez les détails de l'abonnement à l'[Étape 4](#step-4) et confirmez que le `streamId` correspond à votre flux cible. |
| La création de l'abonnement échoue | Le compte LDP et le Load Balancer se trouvent dans des comptes OVHcloud différents. | Utilisez un flux de données qui appartient au même compte OVHcloud que le Load Balancer. |
| Seule une partie du trafic est journalisée | Les listeners UDP ne sont pas transférés. | N'attendez des logs que pour les listeners `tcp`, `http` et `https`. |
| Impossible de trouver le `serviceName` | Le nom interne du Load Balancer est incertain. | Récupérez-le depuis l'espace client ou avec l'appel `GET /ipLoadbalancing` de l'[Étape 1](#step-1). |

Si les étapes ci-dessus ne résolvent pas le problème :

1. Rassemblez l'`operationId`, le `subscriptionId`, le `serviceName` et le `streamId` concernés.
2. Contactez le [support OVHcloud](https://help.ovhcloud.com/) et fournissez les informations de diagnostic collectées ci-dessus.
