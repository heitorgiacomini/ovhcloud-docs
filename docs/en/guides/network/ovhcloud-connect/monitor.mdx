## Objective

Monitoring your OVHcloud Connect service ensures that the connection is healthy, performant, and meeting your expectations. This guide covers the tools and metrics available.

Log in to your <ManagerLink to="/">OVHcloud Control Panel</ManagerLink> and open the <code className="action">Bare Metal Cloud</code> section, then go to <code className="action">Network</code> > <code className="action">OVHcloud Connect</code>.

## Monitoring tools

### OVHcloud Control Panel

The primary interface for checking your connection provides visibility into the following information:

| Item | Description |
|---|---|
| **Connection status** | Whether the physical link is up or down |
| **Optical values** | IN/OUT optical light levels on the physical port |
| **Service details** | PoP, bandwidth, vRack association, configuration |

BGP session state and learned/advertised routes are retrieved through the on-demand diagnostics described below. OVHcloud Connect does not expose a bandwidth-usage dashboard or alerting feature in the Control Panel.

### OVHcloud API

For programmatic monitoring and integration with your own tools:

```python
import ovh

client = ovh.Client(endpoint='ovh-eu')

service_name = "your-occ-service-uuid"

# Get service status
service = client.get(f"/ovhCloudConnect/{service_name}")
print(f"Status: {service['status']}")

# Get PoP configuration and BGP state
pop_config = client.get(f"/ovhCloudConnect/{service_name}/config/pop")
print(pop_config)
```

> Full API reference: [eu.api.ovh.com/console](https://eu.api.ovh.com/console/?section=%2FovhCloudConnect&branch=v1)

### Your own monitoring tools

OVHcloud does not provide traffic-usage graphs or alerting for OVHcloud Connect, so continuous monitoring is done from your own side. On your edge router and monitoring stack you can, for example:

- **SNMP** — Poll your router's interfaces for traffic counters, error rates, and interface status.
- **BGP monitoring** — Use tools like `bgpstream`, `exabgp`, or your router's built-in monitoring to track BGP session stability and prefix changes.
- **Ping / latency probes** — Set up regular pings or latency measurements between your on-premises network and OVHcloud resources.
- **Third-party platforms** — Tools like Datadog, Zabbix, PRTG, or Grafana can aggregate metrics from your own infrastructure.

These are generic, customer-side practices and not OVHcloud features.

## On-demand diagnostics

You can launch on-demand diagnostics from the OVHcloud Control Panel to get a point-in-time status report of your OVHcloud Connect service. Each diagnostic runs in real time against the OVHcloud-side equipment and returns a result you can view or download.

### Available diagnostics

**Layer 3 mode:**

| Diagnostic type | Description |
|---|---|
| **Default** | Fetches the BGP session state and related information. In the Control Panel this is triggered by the <code className="action">BGP Peering Test</code> button. |
| **Routes** | Fetches the routing table learned by OVHcloud via BGP (routes received from your side). |
| **Advertised-Routes** | Fetches the routing table advertised by OVHcloud to your side. |

**Layer 2 mode:**

| Diagnostic type | Description |
|---|---|
| **MAC Address** | Fetches the list of MAC addresses seen on the Layer 2 segment between your network devices and the vRack. |

### Launch a diagnostic

1. Open the OVHcloud Connect service you want to diagnose.
2. At the bottom of the "POP Configuration" panel, in the "Diagnostic POP" segment, click the ellipsis button <code className="action">...</code>.
3. Select the diagnostic to run — for example <code className="action">BGP Peering Test</code> in Layer 3 mode, or <code className="action">Get the list of my MAC addresses</code> in Layer 2 mode.
4. Confirm by clicking <code className="action">Launch diagnostic</code>.

### Retrieve a result

1. Open the <code className="action">Diagnostics</code> tab of the service. Each diagnostic is listed with its ID and timestamp.
2. Click the ellipsis button <code className="action">...</code> next to the entry.
3. Select <code className="action">See result</code> to open the output in a new window, or <code className="action">Download result</code> to save a `.txt` file.

### Limits

| Limit | Value |
|---|---|
| **Retention** | Only diagnostics initiated **within the last seven days** are accessible. Download and archive the ones you need to keep. |
| **Rate limit** | **10 diagnostics per type, per service, per 24 hours.** This applies independently to each diagnostic type (Default, Routes, Advertised-Routes, MAC Address). |

:::info

Diagnostics are also available programmatically through the OVHcloud API under the `/ovhCloudConnect/{serviceName}/diagnostic/...` endpoints. Refer to the [API console](https://api.ovh.com/) for the full list.

:::

## What to watch for

<img className="thumbnail" alt="What to watch for" src="/images/network/ovhcloud-connect/monitor/fig-1.svg" loading="lazy" />

Because OVHcloud Connect exposes on-demand diagnostics rather than continuous metrics, watch for these conditions from your own monitoring:

| Condition | How to detect it | Action |
|---|---|---|
| **Link down** | Physical port state changes to "down" (Control Panel / your router) | Check cross-connect, SFP, and contact data centre or provider |
| **BGP session down** | BGP session state changes from "Established" (run the **Default** diagnostic or check your router) | Check router configuration, peer reachability, and firewall rules |
| **Prefix count change** | Unexpected increase or decrease in received/sent prefixes (run the **Routes** / **Advertised-Routes** diagnostics or check your router) | Investigate route leaks or configuration changes |

## Monitoring commands on your router

You can also verify the session from your own edge router using your vendor's standard BGP and interface show commands.

## Best practices

- **Monitor from both sides** — Check the status and optical values in the OVHcloud Control Panel, and traffic/BGP metrics on your own router.
- **Baseline your metrics** — Record normal bandwidth, latency, and prefix counts on your side so you can detect anomalies.
- **Automate alerting on your side** — Set up automated notifications for critical events in your own monitoring stack.
- **Run diagnostics when needed** — Use the on-demand diagnostics to confirm BGP state and route exchange when investigating an issue.
- **Test failover** — If you have a Multi-AZ setup, periodically test failover and verify that your monitoring detects the switch.
