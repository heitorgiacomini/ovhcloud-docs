## Objective

This guide describes a reference design for serving a standard HTTP/HTTPS web application behind an OVHcloud Load Balancer service. It explains how the building blocks fit together, how a request travels from a visitor to a backend server, and which design decisions matter for a single-application deployment.

This is a conceptual reference, not a step-by-step procedure. Each configuration step links to a dedicated task guide.

**This guide explains the reference design for an HTTP/HTTPS web application behind an OVHcloud Load Balancer service.**

**In this guide, you will learn:**

- The components of an HTTP/HTTPS reference design.
- How a request flows from the visitor to a backend server.
- The recommended build order and the key design decisions.
- The limitations of this single-application design.

## Requirements

- An [OVHcloud Load Balancer](/links/network/load-balancer) service in your OVHcloud account.
- Access to the <ManagerLink to="/">OVHcloud Control Panel</ManagerLink>.
- One or more backend web servers reachable from the Load Balancer.
- A domain name you can point at the Load Balancer (required for the HTTPS part of the design).

## Introduction

The OVHcloud Load Balancer distributes incoming traffic across multiple backend servers using a configurable balancing algorithm. A Load Balancer service has four parts:

- **Frontends** — the entry points that listen on a public IP address and a port, and expose the service on the Internet.
- **Server farms** — groups of backend servers, with the balancing algorithm and health probes that decide where traffic is sent.
- **Servers** — the individual backends inside a farm.
- **SSL/TLS certificates** — the certificates that authenticate the service and encrypt HTTPS connections.

For a conceptual overview of the product, refer to [What is OVHcloud Load Balancer](/guides/network/load-balancer-revamp/what-is-load-balancer). For definitions of the terms used below, see the [glossary](/guides/network/load-balancer-revamp/glossary).

## Reference design

This section presents the topology of the reference design, the request flow, and the decisions you make when you build it.

### Topology

The design exposes a single web application through two frontends that share one HTTP server farm:

- An **HTTP frontend** listening on port 80.
- An **HTTPS frontend** listening on port 443, with the `SSL` option enabled and an SSL/TLS certificate attached.

Both frontends route to the same HTTP server farm, which balances traffic across one or more backend web servers. This keeps a single backend pool behind both entry points, so the application is served identically over HTTP and HTTPS.

### Request flow

The path a request takes depends on whether the visitor connects over HTTP or HTTPS:

| Step | HTTP (port 80) | HTTPS (port 443) |
|---|---|---|
| 1. Connection | The visitor connects to the public IP address on port 80. | The visitor connects to the public IP address on port 443. |
| 2. TLS | Not applicable. | The HTTPS frontend terminates TLS using the attached SSL/TLS certificate. |
| 3. Frontend | The HTTP frontend accepts the request. | The HTTPS frontend accepts the decrypted request. |
| 4. Routing | The frontend forwards the request to the default HTTP server farm. | The frontend forwards the request to the default HTTP server farm. |
| 5. Balancing | The farm selects a backend server using the configured algorithm, skipping any server marked down by the health probe. | Same as HTTP. |
| 6. Response | The selected server responds; the Load Balancer relays the response to the visitor. | The Load Balancer re-encrypts the response and relays it to the visitor. |

TLS is terminated at the Load Balancer, so the connection between the Load Balancer and the backend servers is plain HTTP in this design. Keep the backend network private or trusted.

### Design decisions

The following decisions shape the reference design. Each one is documented in a dedicated guide.

| Decision | Options | Notes |
|---|---|---|
| Balancing algorithm | `Round Robin`, `Least Connections`, `Source Hash`, `URI Hash`, `First Available` | `Round Robin` is the common default for stateless web traffic. See [configure server farms](/guides/network/load-balancer-revamp/configure-server-farms). |
| Health probe | HTTP probe recommended when the farm has more than one server | Without a probe, traffic may be routed to an unresponsive backend. See [configure health probes](/guides/network/load-balancer-revamp/configure-health-probes). |
| Session stickiness | `None`, `Cookie`, `Source IP` | Enable stickiness only if the application keeps server-side session state. See [configure stickiness](/guides/network/load-balancer-revamp/configure-stickiness). |
| Certificate strategy | Imported certificate or a certificate managed automatically by the Load Balancer | A managed certificate is renewed automatically. See [configure SSL certificates](/guides/network/load-balancer-revamp/configure-ssl-certificates). |
| TLS profile | `Modern (TLS 1.3)`, `Intermediate (TLS 1.2+)` | Choose `Modern (TLS 1.3)` unless older clients must be supported. |

## Build order

The order in which you create the elements matters, because some objects depend on others.

:::warning
Server farms must exist before you can attach servers or set a frontend's default farm. Create the farm first, then its servers, then the frontends, and attach the SSL/TLS certificate last.
:::

Recommended sequence:

1. **Create the HTTP server farm.** Define the protocol, the datacentre, and an explicit port (usually 80). For more than one server, configure an HTTP health probe. See [configure server farms](/guides/network/load-balancer-revamp/configure-server-farms).
2. **Add the backend servers.** Add each backend by its IPv4 address. See [configure server farms](/guides/network/load-balancer-revamp/configure-server-farms).
3. **Create the HTTP frontend (port 80).** Set its default route to the HTTP server farm. See [configure frontends](/guides/network/load-balancer-revamp/configure-frontends).
4. **Add the SSL/TLS certificate.** Import an existing certificate or order one managed by the Load Balancer. See [configure SSL certificates](/guides/network/load-balancer-revamp/configure-ssl-certificates).
5. **Create the HTTPS frontend (port 443).** Enable the `SSL` option and route it to the same HTTP server farm. See [configure frontends](/guides/network/load-balancer-revamp/configure-frontends).
6. **Apply the configuration.** Changes take effect only after they are explicitly applied to every zone of the service. See [manage via Control Panel](/guides/network/load-balancer-revamp/manage-via-control-panel).

:::tip
To avoid downtime when you point your domain at the Load Balancer for certificate validation, configure and test the HTTP frontend on port 80 first. The site stays reachable while you validate and enable HTTPS.
:::

To manage this design as code, use the OVHcloud Terraform provider. Frontends and applying the configuration are not available as Terraform resources; manage them through the API or the Control Panel.

## Considerations and limitations

This reference design targets a single web application served over HTTP and HTTPS. Be aware of the following constraints.

| Limitation | Details |
|---|---|
| Single application | Both frontends route to one default server farm. Serving several distinct applications requires HTTP routes. See [configure HTTP routes](/guides/network/load-balancer-revamp/configure-http-routes). |
| TLS termination | TLS is terminated at the Load Balancer; traffic to the backends is plain HTTP. Keep the backend network private or trusted. |
| Single zone | This design assumes one zone. Multi-zone resilience is a separate design. See [resilient multi-zone architecture](/guides/network/load-balancer-revamp/architecture-resilient-multi-zone). |
| Configuration apply | No change is live until it is applied to every configured zone. |
| HSTS | If you enable HSTS on the HTTPS frontend, the choice is not reversible for clients that have already recorded it. Enable it only after HTTPS is fully tested. |
