## Objective

This guide walks you through deploying your first HTTP/HTTPS service on the OVHcloud Load Balancer, from zero to a working configuration. You order the service, build a server farm with backend servers, create the frontends that expose the service on the Internet, attach an SSL/TLS certificate for HTTPS, apply the configuration, then point your DNS records to the Load Balancer and verify that traffic flows.

**In this guide, you will learn how to:**

- Order an OVHcloud Load Balancer and locate it in the Control Panel.
- Create an HTTP server farm and attach one or more backend servers.
- Create an HTTP frontend on port 80 and an HTTPS frontend on port 443.
- Attach an SSL/TLS certificate to enable HTTPS.
- Apply (refresh) the configuration so changes go live.
- Point your DNS records at the Load Balancer and verify the result.

:::warning
The order in which you create elements matters. A server farm must exist before you attach servers or reference it from a frontend, and frontends must be created after the farm so you can select the farm as their default route. Follow the sections in the order presented.
:::

## Requirements

- An active <ManagerLink to="/">OVHcloud account</ManagerLink>
- Access to the <ManagerLink to="/">OVHcloud Control Panel</ManagerLink>
- An [OVHcloud Load Balancer](/links/network/load-balancer) offer (ordered in the first step below if you do not have one)
- At least one backend server reachable from the Load Balancer, identified by its IPv4 address
- A registered domain name whose DNS zone you can edit (required for HTTPS and for the verification step)
- For the API channel: OVHcloud API credentials. Refer to the [First steps with the OVHcloud API](/guides/manage-and-operate/api/first-steps) guide.

## Introduction

The OVHcloud Load Balancer distributes incoming traffic across multiple backend servers, improving availability and scalability for your applications. A Load Balancer configuration is built from four parts: server `farms` (and the `servers` they contain), `frontends` that expose the service on the Internet, `routes` that connect frontends to farms, and `SSL/TLS` certificates that encrypt connections. This guide covers the most common case: distributing web traffic over HTTP and HTTPS. For a conceptual overview, see [What is OVHcloud Load Balancer](/guides/network/load-balancer-revamp/what-is-load-balancer).

### Overview <a name="overview"></a>

Before you start, understand how a request reaches your backend. The frontend listens on a public IP and port, hands the connection to a route, and the route directs it to a server farm, which selects one of its servers. The diagram below shows the flow for an HTTP/HTTPS deployment with a single shared farm.

<img className="thumbnail" alt="Overview <a name=overview></a> diagram" src="/images/network/load-balancer-revamp/quickstart-http-https/fig-1.svg" loading="lazy" />

Both frontends route to a single HTTP farm. The HTTPS frontend also terminates TLS using the certificate you attach in [Step 5](#certificate).

If you do not yet have a Load Balancer, order one before configuring it. Skip this step if your service already appears in the Control Panel.

<Tabs>

2. Click `Order` and follow the ordering funnel to select your offer, region, and zone.

</Tab>

The `serviceName` returned (for example `loadbalancer-a1b2c3...`) is the identifier used in every call below.

</Tab>
</Tabs>

Once the service is active, open it in the Control Panel. The configuration tabs are `Server Farms`, `Frontends`, `SSL Certificates`, `Subnet`, `Statistics`, `Logs`, `Tasks`, and `Quota`.

### Step 2 — Create a server farm <a name="farm"></a>

The server farm receives traffic from the frontends and distributes it across its backend servers. Create the HTTP farm first, because frontends and servers reference it.

<Tabs>
<Tab label="Control Panel">

1. Open the `Server Farms` tab.
2. Click `Create farm`.
3. Fill in the fields. For a simple configuration, the `Protocol` and the datacentre are mandatory. Define a `Port` explicitly — typically port 80 for a web service. If no port is set, the Load Balancer reuses the frontend port, and health probes may not behave as expected.
4. If you plan to add several servers, select a balancing algorithm (for example `Round Robin` or `Least Connections`) and configure a health probe so the Load Balancer can automatically remove an unresponsive server.
5. Click `Create` to save the farm.

{/* DRAFT: To screenshot - the Create Server Farm form with protocol and port filled in */}

The new farm appears in the list under the `Server Farms` tab.

</Tab>
<Tab label="OVHcloud API">

Create an HTTP farm:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/http/farm"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3` |
| `zone` (body) | Yes | The zone the farm is created in. | `gra` |
| `port` (body) | No | Default backend port for the farm. | `80` |
| `balance` (body) | No | Balancing algorithm. | `roundrobin` |
| `displayName` (body) | No | Human-readable farm name. | `web-farm` |

List existing HTTP farms to retrieve the generated `farmId`:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/http/farm"} />

</Tab>
</Tabs>

### Step 3 — Add servers to the farm <a name="server"></a>

A farm needs at least one backend server to handle requests. Add your web servers to the farm created in the previous step.

<Tabs>
<Tab label="Control Panel">

1. In the `Server Farms` tab, click the farm to select it. The list of its servers appears below, along with the `Add server` button.
2. Click `Add server`.
3. Enter the server details. Only the `IPv4 Address` field is mandatory. If a server uses a different port from the farm default, you can override it here, though a uniform configuration is easier to maintain.
4. Click `Create` to add the server.

{/* DRAFT: To screenshot - the Add server form with an IPv4 address entered */}

The server appears in the farm's server list under the `Server Farms` tab.

</Tab>
<Tab label="OVHcloud API">

Add a server to the farm, using the `farmId` from the previous step:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/http/farm/\{farmId\}/server"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3` |
| `farmId` | Yes | The farm the server is added to. | `12345` |
| `address` (body) | Yes | Backend server IPv4 address. | `203.0.113.10` |
| `status` (body) | Yes | Operational state of the server. | `active` |
| `port` (body) | No | Per-server port override. | `8080` |

List the servers in the farm to confirm they were added:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/http/farm/\{farmId\}/server"} />

</Tab>
</Tabs>

### Step 4 — Create the HTTP frontend <a name="frontend-http"></a>

The frontend exposes your service on the Internet and forwards traffic to the farm. Start with a plain HTTP frontend on port 80 so you can validate the configuration before adding HTTPS.

<Tabs>
<Tab label="Control Panel">

1. Open the `Frontends` tab.
2. Click `Create frontend`.
3. Fill in the fields. For a simple configuration, the `Protocol`, the `Port` (80 for standard HTTP), and the datacentre are mandatory. To listen on several ports, enter a comma-separated list or a range in the form `START_PORT-END_PORT`.
4. Set the `Default route` to the farm you created so traffic is routed to it.
5. If you have routed Additional IPs to the Load Balancer, you can attach the frontend to one or more of them.
6. Click `Create` to save the frontend.

{/* DRAFT: To screenshot - the Create Frontend form with port 80 and the default route set to the farm */}

The frontend appears in the list under the `Frontends` tab.

</Tab>
<Tab label="OVHcloud API">

Create an HTTP frontend:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/http/frontend"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3` |
| `zone` (body) | Yes | The zone the frontend is created in. | `gra` |
| `port` (body) | Yes | Listening port(s). | `80` |
| `defaultFarmId` (body) | No | Farm that receives the traffic. | `12345` |
| `ssl` (body) | No | Enable TLS termination (leave disabled for HTTP). | `false` |

</Tab>
</Tabs>

### Step 5 — Attach an SSL/TLS certificate <a name="certificate"></a>

To serve traffic over HTTPS, the Load Balancer needs an SSL/TLS certificate. You have two options, depending on your needs and existing setup:

- **Import an existing certificate** that you ordered and manage yourself. You are responsible for renewing it before it expires and updating it on the Load Balancer.
- **Order a certificate managed by the Load Balancer** (Let's Encrypt), which is validated, installed, and renewed automatically.

:::info
A managed certificate requires that the domain already points to the Load Balancer: the `A` and `AAAA` records of your domain must resolve to the IPv4 and IPv6 of the Load Balancer (or one of its Additional IPs). To avoid downtime, first deploy and test the HTTP configuration on port 80, then order the managed certificate. If your site is already on HTTPS elsewhere, import your current certificate, deploy and test the HTTPS frontend, then order a managed certificate for the same domain — it is taken into account automatically before the old one expires.
:::

Certificates configured on the service are automatically available to every frontend that has the SSL option enabled.

<Tabs>
<Tab label="Control Panel">

1. Open the `SSL Certificates` tab.
2. To import an existing certificate, click `Add Certificate` and provide the private key and certificate (both mandatory), then click `Create`.
3. To order a managed certificate, start the Let's Encrypt ordering flow, enter your domain, confirm it points to the Load Balancer, and follow the validation emails you receive.
4. When configuring the frontend in the next step, you can choose a TLS configuration profile such as `Modern (TLS 1.3)` or `Intermediate (TLS 1.2+)`.

{/* DRAFT: To screenshot - the SSL Certificates tab showing the Add Certificate action */}

The certificate appears in the list under the `SSL Certificates` tab once added or issued.

</Tab>
<Tab label="OVHcloud API">

Import an existing SSL/TLS certificate:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/ssl"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3` |
| `certificate` (body) | Yes | PEM-encoded certificate. | `-----BEGIN CERTIFICATE-----...` |
| `key` (body) | Yes | PEM-encoded private key. | `-----BEGIN PRIVATE KEY-----...` |
| `chain` (body) | No | Intermediate certificate chain. | `-----BEGIN CERTIFICATE-----...` |
| `displayName` (body) | No | Human-readable certificate name. | `example-com` |

To order a managed (Let's Encrypt) certificate instead:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/freeCertificate"} />

List the configured certificates:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/ssl"} />

</Tab>
</Tabs>

### Step 6 — Create the HTTPS frontend <a name="frontend-https"></a>

With a certificate available, create a second frontend that listens on port 443 and terminates TLS. It routes to the same farm as the HTTP frontend.

<Tabs>
<Tab label="Control Panel">

1. Open the `Frontends` tab and click `Create frontend`.
2. Set the `Port` to 443 and enable the SSL option so the frontend terminates HTTPS.
3. Select the certificate under `TLS Certificate`.
4. Set the `Default route` to the same farm used by the HTTP frontend.
5. Optionally enable HSTS. With HSTS, browsers use HTTPS for every future visit, which protects against downgrade attacks.
6. Click `Create` to save the frontend.

{/* DRAFT: To screenshot - the Create Frontend form with port 443, SSL enabled, and a TLS certificate selected */}

:::warning
HSTS cannot be undone once browsers have recorded it. Enable it only after you have confirmed that HTTPS works correctly without side effects.
:::

</Tab>
<Tab label="OVHcloud API">

Create an HTTPS frontend with SSL enabled:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/http/frontend"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3` |
| `zone` (body) | Yes | The zone the frontend is created in. | `gra` |
| `port` (body) | Yes | Listening port. | `443` |
| `ssl` (body) | Yes | Enable TLS termination. | `true` |
| `defaultFarmId` (body) | No | Farm that receives the traffic. | `12345` |
| `hsts` (body) | No | Enable HTTP Strict Transport Security. | `false` |

</Tab>
</Tabs>

### Step 7 — Apply the configuration <a name="apply"></a>

Configuration changes are not live until you apply (refresh) them in each zone of your service. This lets you stage a complex change and push it in a single step. If your service spans several zones, apply the configuration to each zone.

<Tabs>
<Tab label="Control Panel">

1. Return to the Load Balancer service home page.
2. Click the `...` menu next to the service name and select the apply-configuration action.
3. Select the zones to deploy and confirm.

{/* DRAFT: To screenshot - the apply-configuration action and the zone selection dialog */}

</Tab>
<Tab label="OVHcloud API">

Apply the pending configuration changes:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/refresh"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3` |
| `zone` (body) | No | Limit the refresh to a single zone. | `gra` |

Review what will change before applying:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/pendingChanges"} />

</Tab>
</Tabs>

### Step 8 — Point your DNS records <a name="dns"></a>

For visitors to reach your service through the Load Balancer, your domain must resolve to the Load Balancer addresses. Update your domain's DNS zone so the `A` and `AAAA` records point to the IPv4 and IPv6 of the Load Balancer (or one of its Additional IPs).

Find the Load Balancer addresses in the Control Panel service summary, or via the API:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}"} />

A typical zone file change looks like this:

```text
www.example.com.   3600   IN   A      203.0.113.50
www.example.com.   3600   IN   AAAA   2001:db8::50
```

:::tip
Lower the record TTL a few hours before the change so the cutover propagates quickly. Raise it again once traffic is confirmed.
:::

DNS changes can take time to propagate. Verify the records have updated before testing:

```bash
dig +short www.example.com A
dig +short www.example.com AAAA
```

### Step 9 — Verify <a name="verify"></a>

With the configuration applied and DNS pointing at the Load Balancer, confirm that traffic flows over both HTTP and HTTPS.

```bash
# HTTP frontend (port 80) should respond
curl -I http://www.example.com/

# HTTPS frontend (port 443) should respond with a valid certificate
curl -I https://www.example.com/

# Inspect the served certificate
openssl s_client -connect www.example.com:443 -servername www.example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -dates
```

Use the table below to confirm each part of the deployment.

| Check | How | Expected result |
|---|---|---|
| Backend server health | `Server Farms` tab, or `GET /ipLoadbalancing/{serviceName}/status` | Servers reported as up / active |
| HTTP frontend | `curl -I http://www.example.com/` | `HTTP/1.1 200` (or your app's response) |
| HTTPS frontend | `curl -I https://www.example.com/` | `HTTP/2 200` with a valid certificate |
| Certificate | `openssl s_client ...` | Subject matches your domain, dates valid |
| Configuration applied | `GET /ipLoadbalancing/{serviceName}/pendingChanges` | Empty list (no pending changes) |

If every check passes, your HTTP/HTTPS Load Balancer is live.

### Troubleshooting <a name="troubleshooting"></a>

The table below lists the most common issues encountered during a first deployment.

| Issue | Possible cause | Solution |
|---|---|---|
| Changes do not appear for visitors | Configuration not applied | Apply (refresh) the configuration in every zone — see [Step 7](#apply). |
| Site unreachable after DNS change | DNS not yet propagated, or records point elsewhere | Verify with `dig +short`; lower the TTL and wait for propagation. |
| Managed certificate order fails | Domain does not resolve to the Load Balancer | Point the `A` and `AAAA` records to the Load Balancer first, then re-order. |
| Backend marked down | Health probe misconfigured or backend not listening on the farm port | Confirm the farm `Port`, the backend port, and the probe settings. See [Configure health probes](/guides/network/load-balancer-revamp/configure-health-probes). |
| 503 returned by the frontend | No active server in the farm, or wrong default route | Confirm the farm has at least one active server and the frontend's default route targets it. |

For automation of this deployment, the OVHcloud Terraform provider exposes resources such as `ovh_iploadbalancing_http_farm`, `ovh_iploadbalancing_http_farm_server`, and `ovh_iploadbalancing_http_route` to build farms, servers, and routes. Frontends and applying (refreshing) the configuration are not managed by Terraform — handle them through the OVHcloud API or the Control Panel. See the [automation guide](/guides/network/load-balancer-revamp/automation).
